Sqrt 家族确证 + 一次 ABI 踩坑 —— 2026-10-10 14:55
============================================================================
新增 2 个目标（14/14 装上，4/4 辅助函数）：
  cfx_sqrt      0x1B489D0  INPUT_GUARD
  cfx_safe_sqrt 0x1B4C600  OBSERVE

定位：Linux 里调用 Sqrt 的只有 4 个函数，其中 CalcDistance 同时调 Sqrt 与 SafeSqrt
且带独特常量 0xf4241(=1000001)。按该常量在 Windows 侧得 3 候选，其一含 CFixedPoint
专属魔数 0x29f16b11c6d1e109 -> 读体确认是 CalcDistance 同构体 -> 它调的 0x1B489D0
就是 Sqrt。再由 Sqrt 的调用者顺出 0x1B4C600 = SafeSqrt() const。

**踩的坑**：我把两个都按 (out, src) 写，Sqrt 对、SafeSqrt 反了。
探针立刻暴露：SafeSqrt 的返回槽一直是预置哨兵 0x5A5A5A5A5A5A5A5A
(= 6510615555426900570)，五个输入全"返回"同一个数。
函数体显示 Sqrt 是 *param_1 = result，SafeSqrt 是 *param_2 = result。
教训：同类相邻成员的参数顺序不一定一致，不能类推。

修正后的探针（ABI 正确的证据）：
  探针 Sqrt     x=100000 (1.0)      -> 100001   (1.0000)     sqrt(1)=1        OK
  探针 Sqrt     x=10000000000 (1e5) -> 31622927 (316.2293)   sqrt(1e5)=316.2278  误差 4.6e-6
  探针 Sqrt     x=1 (1e-5)          -> 0                     走 1<x 守卫      OK
  探针 Sqrt     x=-1                -> 0                     INPUT_GUARD 触发 OK
  探针 SafeSqrt x=100000 (1.0)      -> 100001   (1.0000)                     OK
  探针 SafeSqrt x=10000000000 (1e5) -> 31622790 (316.2279)                误差 4.4e-7
  探针 SafeSqrt x=1 (1e-5)          -> 317      (0.0032)   sqrt(1e-5)=0.003162 OK
SafeSqrt 比 Sqrt 更准，正是它"先缩放进安全域再算"的设计目的。

Sqrt 与 SafeSqrt 的全部调用者都已枚举读体，没有一个是 Linux 那个 10 行包装。
不是"没找到"而是"不存在"；等价保护已被 Sqrt/SafeSqrt 两个钩子覆盖。

diplo_weight 确证 —— NDefines 名字法（第三个方法突破） 2026-10-10 15:04
============================================================================
新增：diplo_weight = CPopJob::CalcDiplomaticWeight @ 0x00838670（OBSERVE）
15/15 钩子装上，实机 115752 次调用，0 条分歧。

难点：这个函数在 Linux 里**没有任何直接调用者**（只有 4 处提及全是它自己），
调用者法完全无效；守卫密度筛出 24 候选、结构偏移 +0x808 命中 0 个。

新方法：Paradox 的 NDefines 名字字符串在 exe .rdata 里是明文。
  1. 找名字 VA（DIPLOMACY_WEIGHT_POP_BASE -> 0x142360e08）
  2. 扫 .text 找 rip-relative 引用 -> 每个名字只有 1 处
  3. 反汇编那处 = 5 指令 thunk：mov rcx,rdx / lea r9,[全局] / lea rdx,["NGameplay"] /
     lea r8,["<名字>"] / jmp <注册函数>
     -> 名字到全局地址的对应关系被直接读出来：
        DIPLOMACY_WEIGHT_POP_BASE      -> 0x143151010
        DIPLOMACY_WEIGHT_POP_HAPPINESS -> 0x143151008
  4. 找「同时读这两个全局」的函数 -> 110843 个函数块里**命中数 = 1**

体形逐条对上 Linux 1177404-1177484：
  param_3+8 虚调用 / param_1+0x18 取 CJobType / param_1+0xec 计数 / param_1+0xe0 数组
  （后两个偏移与 Linux 完全相同）/ (arr)[i*2+1]*100000 / * DAT_143151010/100000 /
  FUN_14067eec0(= HasHappiness) / * DAT_143151008/100000 / *(param_3+0x8b0) 再乘 / 求和写回 sret

顺带解答上轮疑问：Linux 读 param_10+0x808，Windows 读 param_3+0x8b0 ——
这就是按 +0x808 检索命中 0 个的原因。MSVC 布局差异再次实证。

可复用：任何 NDefines::<组>::<名字> 静态成员都能用这三步定位，
读的是编译器自己写的元数据，比函数体指纹可靠。

实机：15/15 钩子，5.8M 次调用，0 条真实 EVENT。
  CalcDiplomaticWeight 115752 次 —— 用户实测最易溢出的目标已覆盖。

更正：cfx_safe_sqrt_int 是**真缺口**，我之前的说法是错的 2026-10-10 15:30
============================================================================
用户问「Linux 能力是否已完全迁移」，我逐条复核时发现自己在 0.1.11 里写错了一句：

  错话：「cfx_safe_sqrt_int 不是缺口，等价保护由 Sqrt(INPUT_GUARD) + SafeSqrt(OBSERVE) 覆盖」
  事实：SafeSqrt(long long) 的溢出点是 p * 100000（p > 9.22e13），
        而 Sqrt / SafeSqrt(const&) 的溢出点在**别的算式**上，不是同一个点。
        装上后者**不能**覆盖前者。已撤回并改写目标表与 README。

为找内联副本做的检索（都失败）：
  (a) 「含 0x2711 + * 10000 且不调用 0x1B4C600/0x1B489D0」的完整内联体
      -> 全库命中 1 个，是 libpng 的 gamma 检查，不是它。
  (b) 「含 * 100000 且调用 0x1B4C600」的 4 个函数
      (0x26C6A0 / 0x33FD20 / 0xA37200 / 0xBF8600) 逐个读过体，
      都是各自独立的除法/缩放计算，不是 p*100000 喂给 SafeSqrt 的形态。

另外复核 Linux 侧实际安装的目标数：**19 个**（try_install 出现 19 次），
与 Windows 的 17 个对照：
  Linux 有 / Windows 无：cfx_safe_sqrt_int（真缺口）、cfx_get_rounded64（COMDAT 折叠，已覆盖）
  => Windows 覆盖 18/19，缺 1 个。

策略分布（Linux 注释统计，OBSERVE 覆盖 11 处钩子）：
  Linux  : EXACT 6 / INPUT_GUARD 2 / OBSERVE 11
  Windows: EXACT 6 / INPUT_GUARD 1 / OBSERVE 10
  EXACT 集合完全相同 —— 「能真正修数值」的能力已对等。

诚实结论：**没有完全迁移**。19 个 hook 目标覆盖 18 个，
唯一缺口是 cfx_safe_sqrt_int 的 INPUT_GUARD（触发阈值 p > 9.22e13，极端 mod 才走到）。

============================================================================
cfx_safe_sqrt_int 结案：不是缺口，Windows 侧无对应代码 2026-10-10 15:43
============================================================================
用户要求"解决它"，结果是把它的性质查清了 —— 它不是待定位，而是**不存在**。

定位过程（用上了之前没用的一条线索：独占报错串）：
  Linux 侧 SafeSqrt(long long) 的**唯一**真实调用点是 MTTHModifyNumber 的 case 0xf
  （脚本 sqrt 运算符），该分支前有独占串
  "script_value/MTTH/weight field: Cannot square root a number that is negative at %s"。
  按该串在 Windows dump 检索 -> **唯一命中 FUN_14033fd20**（= Windows 的 MTTHModifyNumber，
  176 行 switch，每个 case 对应一种脚本运算：case 0xc 取绝对值 / 0xe pow / 0xf sqrt）。

读它的 case 0xf：
    case 0xf:
      if (-1 < (longlong)*param_1) {                   // 非负才走
          puVar4 = FUN_141b4c600(param_1, &local_20);  // = SafeSqrt(CFixedPoint const&)
          *param_1 = *puVar4;
          return 1;
      }
      ... "Cannot square root a number that is negative at %s"   // 负值 -> 报错，不算

**它直接把 param_1（CFixedPoint*）的地址传给引用版 SafeSqrt，没有 p*100000 这一步。**

对照：
  Linux   : SafeSqrt(param_9)          实参是**整数** long  -> 重载内部做 p*100000（溢出点）
  Windows : FUN_141b4c600(param_1, ...) 实参是**指针**      -> 无该步

case 0xf 里 param_1 本来就是定点格式、值已在格式内，所以编译器直接用引用重载，
不需要「整数 -> 定点」换算 —— 那个 p*100000 压根不生成。
**Linux 那条 INPUT_GUARD 保护的是一步 Windows 编译器根本不会生成的运算。**

而且 case 0xf 自己已有负值检查（负 -> 报错返回，不计算），
即 Linux 守卫要防的场景，游戏在本路径上已自行防护。
真正的 sqrt 求值路径已被 cfx_safe_sqrt 钩子覆盖（含 x<0 判定）。

为找内联副本做的检索（都失败，留档）：
  (a) 精确签名「0x2710 + 0xb504f333 + 0x16a09e666 三件套」全库仅 1 处（真函数本身）；
  (b) SafeSqrt 的 6 个调用点逐个反汇编，无一是 p*100000 形态；
  (c) 80 字节窗口搜出的 3 个"疑似内联点"经读体确认是 x*x 乘法辅助（假阳性）。

**最终结论：Linux 的 19 个 hook 目标在 Windows 侧全部覆盖。**
  - cfx_get_rounded64：COMDAT 折叠，与 cfx_get_rounded 同地址，一个钩子覆盖两者
  - cfx_safe_sqrt_int：Windows 侧无对应代码（MSVC 不生成该重载的那步换算）
