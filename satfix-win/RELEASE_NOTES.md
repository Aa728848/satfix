# 发布说明（Release notes）

这个文件是**发布说明的唯一来源**：`tools/package_release.ps1` 会从它抽出对应版本的
那一节，作为 GitHub Release 的正文。改说明改这里，不要在 GitHub 网页上直接改 ——
否则下次发布时会被覆盖，而且没有版本记录。

## 约定

- 每个版本一节，标题格式 `## v<版本>`，与清单里的 `version` 一致。
- 最新的写在**最上面**。
- 发布流程见 `README.md` 的「发布与自动更新」一节。

## v0.5.1

在 v0.5.0（Cygnus 4.6.0 / `0x6AF6BDEC`）基础上处理两处「主动降级」，并修一个启动器报错；仍是回写模式。

### 1. 修：`ship_size_max_hp` 的 `+0x6b8` 在 4.6 已失效 → 纠正为 `+0x6f0`，恢复回写

4.5.3 实测的 `CShipSize + 0x6b8` 在 4.6.0 上已不是 `max_hitpoints`。实机对 320 个 `CShipSize` 对象做「已知脚本船体值反扫」：唯一同时命中全部 11 个基础值（`@transport_hp=100` … `@juggernaut_hp=100000`）的槽位是 **`+0x6f0`**；`+0x6b8` 上是 0/0.75/1.0/1.5 之类小数（别的字段）。偏移改为 `0x6f0` 并恢复回写（仍只认负值，正常正值一律不动）。

### 2. 变量系统（`var_multiply` / `var_add`）适配 4.6 token 键控链 + 恢复回写

4.6 把变量存储改成 token 键控哈希表。已按 4.6 Windows 反汇编逐寄存器确证并接入：token 内联在效果对象 `this+0xc0`（Linux 0xb8），经 `AccessVariablePointer(scope, token)` 取容器；读值走 `CPdxUnorderedMap::FindGet`（`0x0088D120`，值在返回指针处）；写回 `0x0088D260`；操作数 `GetValue(this+0x298, scope)`。

回写判据 `v1 != sat` 已用离线对拍证明**完备且无假阳**：`cfx::add/mul` 是精确饱和运算（800 万组含 INT64 极值随机对拍，与「128 位真值向零截断再夹到 int64」逐位相等、0 反例）；游戏 64 位乘法只在**它自己算错**时才不等于精确值（真值越界，或拆分中间量在 |操作数|≳9e8 时溢出），写回精确饱和值即修复。变量合法为负不触发。

### 3. 修：启动器 `plugins\node_modules` 报错

`plugins\node_modules` 是 MCP 插件的 Node 依赖，落在插件根目录导致启动器把它当插件、报「no stl-plugin.json」。已把它移到 `stellaris-mcp\mcp-server\node_modules`（其 `package.json` 归属处）。

### 验证

- 回写模式构建通过全部离线测试与发布包 25 项合规检查。
- 实机：`ship_size_max_hp` / `var_multiply` / `var_add` 三钩子装载成功、零崩溃；样本 `SAMPLE add_variable v0=200000 d=100000 game=300000 sat=300000 一致`。

## v0.5.0

清单里的名称与说明改成**全英文**（与其它插件一致）：`satfix — Fixed-Point Overflow Guard`。

适配 **Stellaris 4.6.0**（`stellaris.exe` 构建时间戳 `0x6AF6BDEC`）。19 个钩子在实机上全部装载成功
（`共装上 19/19 个钩子`），游戏内目标函数确实被调用（见日志 `首次调用: ...`）。

### 为什么这次改动比往常多

4.6 不只是把函数挪了位置，还改了几处**会让插件算错**的东西。所以这次除了重定位地址，还同步了常量和取法：

- **ModifierType 枚举整体位移**。护盾/装甲/船体的修正类型从 `0x1e/0x1f`、`0x2e/0x2f`、`0x24/0x25`
  变成 `0x20/0x21`、`0x30/0x31`、`0x26/0x27`，船级修正对也从 `0x1c8/0x1c9`、`0x1c6/0x1c7`
  变成 `0x1d4/0x1d5`、`0x1d2/0x1d3`。不改这里，回写模式会把**算错的上限**写进存档。
- **ModifierType 元数据表改成了指针间接寻址**。4.5.3 是 `*(DAT_142814390 + type*0xb0 + 0xa8)`，
  4.6 变成 `mov r15,[rip+…]` 再 `[rcx + r15 + 0xa8]`（指针变量 RVA `0x2A29CF0`，静态映像里是 0、
  启动后才填）。照旧读静态地址会读到垃圾，插件已改成运行时解引用。
- **三张船级修正表的地址更新**（`hull 0x2A2BCA4` / `armor 0x2A2BCE0` / `shield 0x2A2BD1C`），
  相对顺序与间隔和 4.5.3 同构（0x3c = 15 项，4.5.3 是 0x38 = 14 项，4.6 多了一个舰船等级）。

### 两处**主动关掉**的功能（宁可漏报，不可误改）

- **变量系统的影子复算停用**。4.6 把变量存储换成了 token 键控的哈希表：取变量作用域的第二参
  从「字符串指针」变成了「16 位 token」，读值/写回也不再走 `CVariables::GetVariable/SetVariable`。
  旧的四步读回链会把字符串指针当 token 传，属于崩溃风险，所以 `var_multiply` / `var_add` 现在只计数、
  不读回、不复算、不回写。
- **船体尺寸兜底的回写暂停**。它依赖 `CShipSize + 0x6b8` 这个偏移，而该偏移是在 4.5.3 上用活体探针
  实测的，6.0 上还没复核过。写错偏移等于把 `INT64_MAX` 写进别的字段，所以先只观测：钩子照常装、
  检出负值照样记 EVENT，但不回写。复核方法写在源码里（打开 `diag_recompute_calls`，进游戏看一次
  `DIAG HULLMAP ... 命中偏移:`）。

### 顺带发现

4.6 自己给一部分定点换算**加了饱和钳位**（例如 `CFixedPoint::GetRounded(fpml::fixed_point<...,15>)`
新体里出现上界 `0xa7c5ac47` / 下界 `0xffffffff583a53b9`，越界直接写 `0xffffffffffff`）。也就是说游戏侧
部分溢出已经自愈 —— 插件在这些点上只做观测，不重复改。

### 重定位是怎么做的

用 4.5.3 的机器码当密码本做掩码字节扫描（25 个目标里 11 个一击命中），其余靠：
`mov r9d,<ModifierType>` 立即数对（三个上限函数，全库唯一）、独占报错串（船体尺寸兜底）、
`.pdata` 分块形状（外交权重 43/74/524/5/20 逐块相同）、以及调用者法（两个 `ApplyModifierMult` 重载）。
每个目标的证据都写进了 `tools/gen_targets_win.py` 的 `RVA_46` / `EVIDENCE_46`。

## v0.4.2

修 **普通国家（例如地球联合国）研究科技时的闪退**，并补上这一类崩溃的**真正根因**。

### 原因：游戏依赖「被钩函数不破坏寄存器」

4.5.3 是 `/GL`（LTCG，全程序优化）编的。编译器知道
`CFixedPoint::GetRounded` 实际只改 `rax/rcx/rdx`，于是调用方会把值放在
`r10/r11` 里**跨这个调用**使用。实机反汇编（RVA `0xFC5BCC` / `0xFC5BCF`）：

```asm
call 0x141B50CE0      ; GetRounded（我们钩了它）
mov  edx, eax
mov  rcx, r10         ; 调用后继续用 r10
call r11              ; 调用后继续用 r11
```

我们的 detour 是普通 C 函数，会改写 `r10/r11`（尤其首次调用写日志、心跳时）。
于是 `call r11` 跳到一个栈地址 → `c0000005`（DEP 执行违规）。
0.4.1 只修了 `GetRounded(fp15)` 的参数个数，没有解决这条「破坏集」契约，
所以普通国家仍会崩。

### 修了什么

- 19 个钩子全部改为安装**汇编转发桩**（`src/detour_stubs.asm`）：进入时保存
  `rcx/rdx/r8-r11 + xmm0-5`、转发第 5/6 个栈参数，调原来的 C 函数体，返回前恢复 ——
  钩子对寄存器的破坏集变成**空集**，永远不会破坏调用方依赖的值。
- `build.ps1` 增加 `ml64` 汇编步骤（`cl` 不会自动分派 `.asm`）。
- 0.4.1 的 `GetRounded(fp15)` ABI 修正保留 —— 那个错误真实存在，只是不是崩溃原因。

### 验证

- 实机：地球联合国 3 局 + 游牧 1 局，各跑 30 年，全部跑完；单局钩子调用
  **9950 万次**（`GetRounded` 625 万、`Atan2` 5100 万、`ApplyModifierMult` 3125 万），
  0 崩溃、`crashes/` 无新目录。
- 桩的机器码逐条核对（保存/恢复/参数转发/栈对齐）；离线 4 套测试、19/19 钩子签名、
  发布包自检全部通过。

## v0.4.1

修一个会让游戏**直接闪退**的 bug：**游牧国家研究科技时 CTD**。

### 原因

科技成本计算会调用 `CFixedPoint::GetRounded(fpml::fixed_point<...,15> const&)`
（Windows 上的调用者体内有 `TECH_COST_EMPIRE_SIZE` / `TECH_COST_OVERLORD` 两条字符串）。
这个函数是 **sret 两参**形态：`rcx = 输出槽`、`rdx = 输入`；
0.4.0 的 detour 按「单参、输入在 rcx」写，调用原函数时**只转发了 rcx**。

平时 rdx 碰巧还是调用方留下的正确指针，所以多数调用看起来没事；
但 detour 在**第一次调用**时要写一条「首次调用」日志，日志会改写 rdx ——
于是原函数从垃圾指针读 8 字节，科技成本被算成一个垃圾值，后续逻辑继续使用它，
最后表现为「研究科技时闪退」。本地复现的崩溃转储为 `c0000005`、故障地址
`0x7FEE68`（栈地址），与「垃圾值被当成指针继续用」一致。

### 修了什么

- detour 改成正确的 `(out, src)` 两参，并把两个参数**原样**转发；
- 这类只观测的钩子改为**先调原函数、再记账**，避免日志/计数改写参数寄存器；
- 上限重算在虚调用 `ship_size_of(design)` 前加了一道 vtable 合法性闸，
  数据库加载期传入的栈上假指针会被跳过，不再可能跳到垃圾地址。

### 怎么验证的

- 活体探针（`SATFIX_WIN_FORCE=1`）**旧版**：三个不同输入全返回同一个垃圾常数 `679080784`；
  **修复后**：`0 -> 0`、`0x8000 -> 100000`、`-0x8000 -> -100000`（fp15 的 1.0 = 0x8000 = 100000）。
- 实机：游牧开局 `humans3`、小图、三项研究、连跑 3 局各 20 年，全部跑完；
  每局 `GetRounded(fp15)` 实调 20 万次量级，0 崩溃。
- `build.ps1 -Replace` 的 4 套离线测试 + 打包自检全过（19/19 钩子签名校验通过）。

### 建议

游牧局、或研究科技时闪退过的存档，直接升到这一版即可；不需要开新档。

## v0.4.0

适配 **Cygnus v4.5.3**（`stellaris.exe` 构建 `0x6AE49C1B`）。功能与 0.3.1 **完全一样**，
19 个钩子、6 个辅助函数一个不少 —— 只是全部重新对准了新构建的地址。

### 为什么必须更新

游戏从 4.5.2 升到 4.5.3 之后，旧的 0.3.1 会**整体失效**：它的每个地址都带着 16 字节序言
签名做运行时校验，构建对不上就安全停用该目标（这是故意的设计，宁可不工作也不乱改内存）。
所以升了游戏就必须换这一版。

### 这次怎么重新定位的

不是猜的，也不是重新做一遍原始分析：

1. 4.5.2 时期留下的 Ghidra 工程还在，直接把 25 个目标函数在旧 exe 里的**机器码**整段读出来；
2. 用 capstone 把 `call`/`jmp` 的 rel32 位移、RIP 相对寻址的 disp32 **标记为通配**，其余字节逐个比对新 exe 的 `.text`；
3. 命中唯一 = 同一段机器码 = 同一个函数；
4. 再用 PE 的 `.pdata` 异常表（每个函数一条 `RUNTIME_FUNCTION`，`BeginAddress` 就是编译器给的函数起点）独立复核，并比对函数长度是否与 4.5.2 一致。

结果：**25 个地址里 23 个是字节级完全一致**（连函数长度都分毫不差），
另外 2 个各有原因，报告在 README 的「4.5.3 重定位记录」里：
`diplo_weight` 被 `.pdata` 切成 5 个连续块（合计仍是 666 字节，前 178 条指令逐条相同），
`ship_size_max_hp` 有一处显式分支展开（1858 → 1870 字节，指令相似度 0.9941）。

### 安装

启动器 → 插件 → 安装，或直接解压到
`Documents\Paradox Interactive\Stellaris\plugins\satfix\`。

## v0.3.1

补了一个上版漏掉的洞：**舰船设计界面里显示的基础船体值**。

### 修了什么

- **设计界面「船体值」显示成天文数字的负数**。有些 mod 在 `common/ship_sizes/`
  里把 `max_hitpoints` 写得很夸张，游戏读到这种数会算崩，设计界面就会显示成
  一长串负号数字（比如 `-84467440737095.51`），看着就像这船没血。
  现在这种数会被改成游戏能表示的最大值，也就是那个「92 万亿」。

  这个和上版修的护盾、伤害是同一类问题，但**触发的地方不一样**：护盾那条是在
  算上限的时候崩的，这条是在**读 mod 文件的时候**就已经崩了。所以上版的修复碰不到它。

  实测对照（同一个存档、同一个 mod，只切换插件开关）：

  | | 设计界面显示 |
  |---|---|
  | 不开插件 | `-84467440737095.51` |
  | 开插件 | `92233720368547.75` |

  > 说句实话：**别人的 mod 要真的把 `max_hitpoints` 写到 92 万亿以上才会触发**。
  > 我扫了自己这套播放集里的 22 个 mod，最大的才 5 亿，离出问题还差得很远。
  > 所以这更像是「提前把洞补上」，你要是不装那种特别离谱的 mod，可能一直也用不到。

- 上版说过「船体那个数我没亲眼见过它溢出」，**现在见过了** —— 就是上面这次测试。
  当时是专门造了个测试 mod 把它逼出来的。

### 这个构建是**回写模式**（REPLACE=1）

也就是说它**真的会改数值** —— 检出坏掉的数就改成正常上限。这才是能生效的版本。
日志首行会写 `REPLACE=1  satfix-build-mode:write-back`。

> 影子模式（只看看、不改数值）是我们自己测试用的，不发布。
> 它对应 `satfix-build-mode:shadow`，首行 `REPLACE=0`。

## v0.3.0

修了三个后期存档里很烦人的毛病。都是同一件事引起的：mod 把数值堆得太高，游戏算着算着就"翻"了。

### 修了什么

- **护盾突然变成 0**。堆了一堆加成之后，护盾那一栏直接归零，看着像没护盾。
  实际是加成数字太大，游戏算崩了，自己又把结果当 0 处理。
  现在这种情况会改成游戏能表示的最大值 —— 显示成「92 万亿」，很大但至少不是 0。
  装甲理论上也会这样，不过我实测只有护盾触发，装甲一次都没误报。
  船体（舰船血量）也接了同样的处理，但船体那一栏在我测的存档里**从来没溢出过**，
  所以它只有「不会误伤」的实测记录，**没有「溢出时确实修好了」的实测记录**。
  理论上它是安全的（漏算的几项都是加法，只会让估算偏小，而封顶值是天定的那个上限），
  但既然没亲眼见过，就如实说一声。
- **舰船详情里的「伤害」变成负数**（或者大得离谱）。
  那一格是船上所有武器加起来、再乘射速加成。射速加成堆得太夸张时就会算爆。
  现在同样封顶到最大值。**这个只影响面板上显示的数字，不影响实际打出来的伤害** ——
  面板是临时算的，真打起来走的是另一套，不受影响。
- **过一天变慢**。这版把两个拖速度的地方优化了，实测每过一个游戏日明显变快。

### 这个构建是**回写模式**（REPLACE=1）

也就是说它**真的会改数值** —— 检出坏掉的数就改成正常上限。这才是能生效的版本。
日志首行会写 `REPLACE=1  satfix-build-mode:write-back`。

> 影子模式（只看看、不改数值）是我们自己测试用的，不发布。
> 它对应 `satfix-build-mode:shadow`，首行 `REPLACE=0`。

**会改动存档里的数值**，这本来就是它的作用。第一次用建议先备份存档。

改的时候很保守：**宁可漏掉，也不乱改**。只有游戏算出来的数本身就明显不对
（负数、或者明明该有值却是 0）才动手；正常数值哪怕我们内部算得有出入，也只记日志不改。

### 安装

启动器 → 插件 → 安装，或直接解压到
`Documents\Paradox Interactive\Stellaris\plugins\satfix\`。

适配 `stellaris.exe` 构建 `0x6ABEAA3F`（Cygnus v4.5.2）。游戏更新后会被自动跳过，
这是保护而非故障。

### 已知限制

- 只适配上面列出的构建；游戏更新后需要重新确证地址并升版本发布。
- **未与其他插件同时启用测试过**（本机只有 satfix 一个插件）。
- 部分目标只检出、不修改（观测模式），这是有意为之：判据不够硬的地方宁可不改。
- 「伤害」那一格修好后仍是「92 万亿游戏单位」这个上限值 —— 定点格式本身的物理天花板，
  继续往上堆加成只会再次越界。

详见仓库 [README](https://github.com/Aa728848/satfix)。

## v0.2.0

首个发布。Windows 侧 17 个目标实机验证全部装上，Linux 侧 19 个 hook 目标全部覆盖。

### 它做什么

把 Stellaris 的定点算术接上饱和处理。定点数用 `int64` 存、1.0 记作 `100000`，
上限约 9.2e13 游戏单位；mod 堆叠乘法越过之后**不报错**，直接 wrap 成负数 ——
海军容量变负、资源扣成天文数字、外交权重突然为负。

回写路径有端到端验证（同一构建脚本只差一个开关）：

| 构建 | `GetRounded(INT64_MAX)` 返回 |
|---|---|
| shadow | `-92233720368547`（游戏 wrap 后的值，就是那个 bug） |
